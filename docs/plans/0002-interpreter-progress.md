Deviations from the plan made during the implementation:

1. **The `decimal` range is below 10³⁸ in absolute value**, not the whole int128: exactly 38 digits, 20 before the point and 18 after, like `numeric(38, 18)` in PostgreSQL. Overflow is checked against this bound.
2. **`timestamp` in `Value`** is Unix seconds in `Lo` and nanoseconds in `Hi`, not Unix nanoseconds: an int64 of nanoseconds cannot hold the default value `0001-01-01T00:00:00Z` (its range is the years 1678–2262).
3. **String and composite identifiers** live in the arena as one value (`Ref.Len == 1`): this way the kind of the content is visible from the `Value` itself, and comparison, hashing and copying need no schema. uuid and sequence are in `Lo`/`Hi`, as planned.
4. **`page` and `pageRequest`** are composite values of two elements in the arena (`items`, `next` and `size`, `cursor`), like a record without a type.
5. **Call arguments in the engine's arena.** `CommandCall` and `QueryCall` got an `Arena` field: the engine builds `ID` and `Args` in it, and the interpreter copies them into the arena of the unit of work (`Arena.Copy`). So a retry of `Execute` after a version conflict uses the same call, and `Outcome.Release` does not touch the engine's data.
6. **`Outcome` and `QueryOutcome` carry their own arena** (`Arena`); `Release` returns it to the pool (`GetArena`/`PutArena`; arenas over 1 MB are not returned). A pool of the `Outcome`s themselves — in stage 7, if the profile shows a need.
7. **`FindSpec` and `Rows` without Go strings:** the page cursor is a value in the arena (`Cursor`, `Rows.Next`), the page size is the fields `Page`/`Size` instead of `*PageRequest`, the found records are a list in the arena (`Rows.Records`). So a search does not allocate on the interpreter side.
8. **Composite values are built bottom-up** through the arena stack (`Mark`, `Push`, `End`, `Drop`): nested values are allocated before the outer one, and the outer slice is not invalidated by buffer growth. The `Elems`/`Fields` slices are valid until the next allocation.
9. **Decision 9 (bank tests in RFC §26) required changing the bank model** (the author's option "a"): in the old model the engine assigned the account number (`id sequence`) and a test could not learn it, there was no way to top up an account, and `MyAccounts` returns a `page`, which `matches` does not compare. Now `Account` is `id uuid`, the number is passed to `OpenAccount(accountId)` (a repeat is the error `accountExists`), and `SetOverdraft(limit)` of the role `compliance` and the query `Details(accountId) AccountRow` are added. The tests (`bank/bank.test.rr`): all validation errors at once, a transfer within the overdraft, a refusal beyond the overdraft with a rollback, a recipient error cancels the transfer, `forbidden` for someone else's account, someone else's account is not visible. The `id sequence` example in §10.2 is now `Invoice.Id`.
10. **The record codec** (`runtime/record`): records start with the number of fields, and missing fields at the end get their default values — a record of an earlier schema version with fields added at the end reads without a migration. The decoder validates its input (lengths, enums, bool, the `decimal` range, repeats in a `set` and in `map` keys) and does not trust length numbers. Default values from schema literals live there too (`Default`, `Literal`, `Zero`).
11. **`float` equality** follows IEEE 754: `NaN ≠ NaN`, `-0 == 0`; the hash agrees (`-0` is normalized).
12. **Registers are IR slots one to one**, without linear scan: lowering already reuses temporary slots by type, and functions are short. Allocation — in stage 7, if the profile shows a need.
13. **Constants.** The pool is schema literals (`bytecode.Const`), not a static arena: so the format does not depend on the arena layout. `Program.Constants()` builds the static arena at load time. A function's constants take the registers after the slots, and the VM copies them into the frame on entry — every instruction operand is uniform (registers only).
14. **Per-function tables:** call entries (`Func.Sites`, in the plan — `Program.Calls`) and search templates (`Func.Finds`) are kept in the function — shorter numbers, a local disassembly. Access is not duplicated in `Func`: the VM takes it from the schema (`MethodInfo.Access`). There is no position table (`Lines`): the IR has no source positions; failure traces with positions — in stage 8 (item 50).
15. **`int` and `bigint`.** The IR has one integer arithmetic (`add.i64`); the generator picks the `i32` variant (a 32-bit overflow is a failure) by the result type. Numeric built-in functions differ by argument kind (`abs.i32`, `decimal.f64`…), `sum` by element kind; the table `bytecode.Intrinsics` is part of the format. By the author's decision `bigint` has its own schema kind `KindBigint` (`int` is `KindInt`, 32 bits): the record codec checks the `int` range, integer comparisons also have `i32` variants, and `reasonr check --against` treats widening `int` → `bigint` as compatible (RFC §32) and narrowing as a type change.
16. **A record's identifier** is read by a separate operation `rec.id` (in the IR — `rec.get x, id`): entities and projections have no `id` field in the schema. How a record in the VM carries its identifier (the rows of `Find` and `rec.load`) is decided in stage 3.
17. **Jumps:** the IR `br` becomes `br.true`/`br.false` falling through to the next block, and a `jmp` to the next block is dropped. A jump address is a word number, 16 bits: a function is at most 65535 words (otherwise a generation error).
18. **The verifier** (`bytecode.Verify`) checks: decoding, registers (a result only into a slot), fields, types, methods and their kinds, called functions and their kinds, table entries, jumps to instruction starts, a return at the end of the code, the operand kinds of typed operations, conditions and `ret.val`, constants. Built-in errors in `expect.error` — by name (`Site.Name`).
19. **Frames are windows of a shared register stack** of one call from outside; constants are copied into the frame on entry. Nested calls (rules, methods, queries, `check`) are Go recursion with a depth limit. A failure (`vm.Fault`) carries the model function and the instruction address; there are no source positions yet (item 14).
20. **An entity or projection record in a register** is the fields by the schema, then the identifier (`rec.id` reads it). `rec.load` appends the id to the record from `Env.Load`; the engine returns the rows of `Env.Find` with the id as the last value already (the contract is in `reasonr.Rows`). A search without an index is `FindSpec.Index == reasonr.NoIndex`.
21. **Arguments of a call from outside** are checked by the schema: a missing non-optional argument gets the parameter's default value, `PageRequest` — `size 20` (RFC §7.2), otherwise `invalidArgument(path, "required")`; the kind, the `int` range, `decimal`, time, enums, string encoding, a page size of 1…100 and value object `check`s (recursively) — `invalidArgument(path, rule)` with `rule` = `type`, `range`, `encoding`, `check`. The path is `name.field[i]`.
22. **Access** is checked for `CallerUser` and `CallerTest` calls; timers and migrations are not checked. `AccessSelf` and `AccessField` compare `Caller.Subject` with the entity identifier or a field of its state — useful in stage 4.
23. **Standard library semantics the RFC did not define** (chosen during the implementation, approved by the author and put into RFC §8.3): `matches` matches the whole string; `length` is the number of Unicode characters; `between(a, b)` includes both bounds; `list.without(x)` removes every element equal to `x`; `int(x)` of a `float`/`decimal` drops the fraction; `int("x")` and other failed conversions are an execution failure; `round(x, n)` of integers with `n < 0` rounds to tens, hundreds… away from zero; for `float` an infinite or NaN result and division by zero are failures. `string(x)` prints enums by value name, identifiers by their content, durations in the largest exact unit (`90s`, `2h`), value objects as `Type(field: value, …)`.
24. **Performance now:** the query `Account.Details` on a stub — about 290 ns and 1 allocation (the `QueryOutcome` object); instructions are decoded on every run. Optimizations — stage 7.
25. **An entity's state is copied on every event** (copy on write): `apply` gets a new record and `set` writes into it, so a command's snapshot is just a reference to the state at its start, and a nested call of a command of the same entity (reentrant ones included) starts from the current state. Only entities with events get into the unit of work, in load order.
26. **`on` reactions** are called by the instruction `react` (lowering puts it before the return of commands that raise events with reactions) on its function's events in order; fields in a reaction are the snapshot of the calling command, `after` is the current state. The events a function raised are taken off the list when it returns.
27. **The reference `[x]` in a command** is the identifier itself or none; `[id]` of one's own entity — whether it existed at the start of the command, of another — whether it exists now (it was there at load time or got an event in this unit of work). `cmd?` on an entity that does not exist does nothing.
28. **The idempotency key of an external request** is a uuid from a SHA-256 of the root call (type, command, id), `now` and the request number: a repeated run gives the same keys. The order of projection operations and events is a shared counter `Seq` of the unit of work.
29. **A private command called from outside** (`CallerUser`, `CallerTest`) is the error `forbidden`; a timer and a migration may call any command.
30. **Migrations** (`Interpreter.Migrate`, `all T`) moved to stage 5: each iteration of the top-level loop is a separate unit of work with a commit, which is simpler to test together with the in-memory engine.
31. **Unit of work scenarios** are Go tests on the models of `examples/` and `constructs` with golden dumps (`testdata/uow/*.txt`, `go test ./runtime/vm -update`), not separate `testdata/uow/*.rr` modules: the example models already cover every capability of RFC §11.2 and the reaction of the tenant `acme`.
32. **Performance now:** the transfer `Account.Transfer` (two entities, events, a notification) — about 1.1 µs and 10 allocations on a stub.
33. **Search in the in-memory engine scans the rows of the type** with a filter and a sort on every query, instead of ordered index structures: the engine is not on the hot path, and the result and the order are the same (the index keys or the query sort, then the id). Ordered indexes — if large data is ever needed in development mode.
34. **Engine rows** are stored in the canonical encoding (`runtime/record`) and decoded in the row's own arena; so every commit checks that the state reads back. Values of different arenas are compared by `reasonr.Compare` — it became two-arena, like `Equal`.
35. **Search conditions:** ordering comparisons with none are false, as in SQL; in sorting none is less than any value. The page cursor is base64 of the canonical encoding of the sort keys and the id of the last row: rows added before the cursor do not shift the next page. An invalid cursor is an error of `Env.Find` (an execution failure).
36. **`FindSpec.Limit < 0` means no limit:** so `all T` gets the identifiers through `Find` without an index, and no new `Env` method is needed.
37. **`forget` in memory** — after commit the personal fields of the forgotten subject and the personal event arguments in the journal are overwritten with none (non-optional ones with the default value), and the row version grows. `Load` and `Find` no longer return them, unique indexes are released. Data written after `forget` is not erased.
38. **The recipient of a notification without `to`** is the initiator of the root command (`Caller.Subject`); the engine adds it to the `Outcome`. A timer, a migration and a role have no initiator — such a notification is not delivered (W1006).
39. **A migration's unit of work is a command call** in the migration body, not a loop iteration: the VM does not tell iterations of nested loops apart in the bytecode. For an iteration with one call (as in the RFC example) this is the same. Migration units of work go to the engine through the `commit` function, and errors of a unit of work stop the migration. The author's decision (option "a") is in RFC §32, item 3 and §37.1.
40. **The VM runs test steps and checks** (`Machine.RunTest`) through the `vm.Driver` interface: the `then` checks compare values in the test's arena and print them with schema names. `Driver` and `Step` live in the package `vm`, not `testrun`, otherwise an import cycle; `testrun` builds the program, creates an engine per test and prints the report. There are no source positions of steps (item 14): a failure points to the line of the test declaration and the step in language form, with identifiers by the test's variable names (`[d1].Accept() as d1`).
41. **Step sections:** `when` is the first step after `when`, the rest are `then`. Errors of a `given` step (including timers fired during `time passes`), errors of a query in `then` and an execution failure stop the test with a failure. A notification without `to` in `then` matches any recipient.
42. **`--check-determinism`** runs every command twice on the same state (the identifier counters are restored) and compares the results element by element; a difference is the error `memory.ErrNondetermined`. Queries are not repeated: they do not change state.
43. **Identifiers and the clock of the in-memory engine:** version 4 uuids from `Seed` and a counter (`00000000-0000-4000-8000-000000000001`, …), `sequence` — a counter per type; the test clock starts at 2026-01-01T00:00:00Z. Tenant data is separated by separate engines: an engine holds one model.
44. **VM failure messages** (`vm.Fault`) are in one language: `--lang` translated the runner's messages but not the failure text (`--lang` was later removed; every message is English).
45. **Performance now:** all 6 taxi tests (building the program, an engine per test, steps and checks) — about 1.3 ms; the goal of stage 7 is under 50 ms.
46. **Results from pools.** `reasonr.NewOutcome` and `NewQueryOutcome` take a result from the pool together with its slices (`SetErrors`, `NewWork`, `Events`, `FieldValues` copy the data into the result's storage); `Release` returns the arena and the result itself to the pool, and a repeated `Release` does nothing. `run` reuses its slices and entity objects between calls, and the external request key is computed without allocations (the same key as before). Migration results are not pooled: their arena is shared.
47. **What gave the speed:** instructions are decoded once at load time (`Machine.code`), parameter default values are computed in the static arena at load time, the codec caches default records (`Codec.Default` copies a ready one), `Arena.Copy` copies composite values without the build stack, `exec` has no `defer`. Superinstructions, register banks (decision 7) and a HAMT (decision 8) were not needed.
48. **Results on Apple M1 Max** (`make bench`, an Env stub): `Customer.OrderTaxi` — 1.9 µs, `Driver.Accept` — 0.85 µs, `Account.Transfer` — 0.86 µs, `Account.Details` — 0.3 µs, `Driver.FreeDrivers` (a page of 20 rows, the search in the stub not counted) — 4.5 µs, all without allocations; all taxi tests — about 1.3 ms. The goals of §11 are < 2 µs, < 5 µs, < 50 ms.
49. **The check in CI:** `TestAllocs` (`testing.AllocsPerRun` on five typical calls) — a separate step without `-race`: under the race detector `sync.Pool` drops objects on purpose. Benchmarks in CI only run (200 iterations): timing on shared CI machines is unstable, so there are no time thresholds.
50. **Source positions.** IR instructions have a file (a number in `Program.Files`, the path relative to the module directory) and the line of the statement, bytecode functions a table `Func.Lines` (address → file and line, only when the line changes); the IR and bytecode formats are version 2, and the disassembly prints positions (`# order.rr:142`). A VM failure carries the place (`Fault.File`, `Fault.Line`) and the model call stack (`Fault.Stack`), a test failure the line of the step or check (`reasonr test` prints `file:line:` before the message, JSON — the fields `file`, `line`). This closes items 14 and 40.
51. **A bug found by a test is fixed:** an entity rule called from a command did not see the fields of its snapshot. Now a rule gets the frame of the calling function (the snapshot, the entity).
52. **The event fold** is `Machine.Fold`: the state from the event journal (the `apply` functions over the default record). The engine property "state = fold of events" is checked on it; it will also help rebuild state on export.
53. **The verifier checks more:** every slot register is written on every path before it is read (a data flow over the jumps), the number of arguments of built-in functions (the signatures `bytecode.IntrinsicSigs`). The VM also checks value kinds where the verifier does not infer types: the arguments of built-in functions and the operands of structural operations (`len`, `get`, `append`, `page.with`, `in`, `field`, `set` — only in `apply`). A violation is the failure `ErrUnsupported`; it does not happen on compiler programs (checked by the engine fuzz test).
54. **A panic inside the VM does not escape:** `Execute`, `Query`, `Migrate`, `Fold` and `RunTest` turn it into a failure — an arena overflow (`reasonr.ErrArenaFull`, which used to panic) into `ErrLimit`, anything else into `ErrInternal` with the Go stack. The fuzz tests treat `ErrInternal` as an interpreter bug.
55. **Loop iterations are counted by backward jumps**, not by `loop.guard` (it stays in the format but does nothing): for compiler loops this is the same number, and the limit also applies to code without `loop.guard`.
56. **The memory limit of a unit of work** `Limits.Memory` — 64 MB of arena by default, checked on every loop iteration: collections are copied (decision 8), and a loop with `list.with` grows quadratically — fuzzing found a hang at 100,000 allowed iterations. The author's decision, put into RFC §24.3 and §37.1 with the value 64 MB.
57. **Fuzz tests:** `FuzzEngine` (`engine/memory`) — the taxi models (base and `acme`), bank, `constructs` and `testdata/store`; random public commands, queries and clock moves with random arguments, the caller taken from the method's access list (sometimes random); it checks for no panics, only the expected failures (overflow, division by zero, `check`, limits, conversions), the determinism of every command and "state = fold of events". `FuzzExec` (`runtime/vm`) — the bytecode of the examples with code words replaced: if the verifier accepted the program, all its commands and queries run without panics. Found and fixed: reading an unwritten register, `page.with` and `set` over foreign values, a built-in function with a wrong number of arguments, an infinite loop without `loop.guard`, quadratic growth (items 53–56). The corpus of findings is `runtime/vm/testdata/fuzz/FuzzExec`. Both tests are in `make fuzz`; the seed corpus and long sequences run in `go test` (`TestFuzzSeeds`). An hour-long run on 2026-10-04 after the fixes: `FuzzEngine` — 123 million, `FuzzExec` — 88 million executions, no failures (the criterion of stage 8).
58. **The engine's indexes** are not checked for consistency with the storage (a property from the plan): there are no separate index structures in memory (item 33); a search reads the storage every time.
