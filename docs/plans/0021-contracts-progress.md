## L4 design (working notes)

- The value-level store interfaces (records in an arena, `reasonr.*` types) move from `port` to the engine's own package `engine/store` (internal after L7): `Reader`, `UnitStore`, `Unit`, `CommittedUnit`, `TimerSource`, `EffectSource`, `ProjectionStore`, `EventStore`, `RequestQueue`, `StateTransfer`, `EntitySink`, `SchemaStore`, … The kernel, the memory store (the in-memory engines and the working set of a kind with state in memory keep values: no encoding on their hot path), dispatch and the conformance suites use them.
- `port` gets the byte-level store ports under the same names: rows with `State` (canonical JSON without personal values), `Sealed`, subjects; key columns as plain Go values (`int64`, `float64`, `string`, `bool`, `[]byte`, `[16]byte`, decimal strings for numeric and timestamp nanoseconds); searches by key columns; units of work as rows, timers, outbox and request records as opaque bytes; the violated unique index by name. A `port.Layout` of every stored type (table name, key columns `k_…` with their kinds, indexes) is computed by the engine, so the PostgreSQL and MongoDB layouts do not change.
- `engine/store/rows` adapts a byte-level store to the value-level interfaces: layout, key columns, encryption and blind keys (pii), the outbox and request payloads (storekit) — the code that was in `postgres/layout.go`, `mongodb/store.go` and their `personal.go`.
- PostgreSQL and MongoDB implement the byte-level ports and import only `port` and `registry`.
